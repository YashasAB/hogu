Dating module tables
1) dating_users
Holds the dating user’s core account + profile.
id — string (cuid), primary key.
phone_e164 — string, unique, required. (Store in E.164 format, e.g. +919876543210; max 20 chars.)
password_hash — string, required. (argon2/bcrypt hash.)
name — string, required (max 100).
dob — date, required (use DateTime in Prisma; store date portion).
Profile text fields
profession — string, optional (max 120).
dreams — string, optional (max 500).
five_year_goal — string, optional (max 500).
what_i_want_in_partner — string, optional (max 500).
why_partner_would_like_me — string, optional (max 500).
Single-value preferences (store as strings from allowed sets below)
physical_activity — string, optional. Allowed set: "RARELY" | "SOMETIMES" | "REGULAR" | "ATHLETE".
date_budget — string, optional. Allowed set: "_500_1000" | "_1000_2500" | "_2500_5000" | "_5000_PLUS".
instagram_handle — string, optional (max 64, store without link).
diet — string, optional. Allowed: "VEG" | "EGG" | "NON_VEG" | "VEGAN" | "JAIN".
drinking — string, optional. Allowed: "NEVER" | "SOCIALLY" | "OFTEN".
smoking — string, optional. Allowed: "NO" | "SOCIALLY" | "YES".
Timestamps
created_at — timestamp, default now.
updated_at — timestamp, auto-update on write.
Indexes / keys
PK: (id)
Unique: (phone_e164)
Notes
Do not add a timezone field.
Validate allowed sets at the app layer (don’t use DB enums to avoid migration pain).
2) dating_user_photos
Stores Replit Object Store references. App enforces exactly 3 photos per user.
id — string (cuid), primary key.
user_id — string, required (logical FK → dating_users.id).
object_key — string, required.
Example key format: dating/photos/<userId>/<uuid>.<ext>
object_url — string, optional (public/CDN URL if you mint one; else null).
sort_order — int, default 0 (use 0,1,2 to order the 3 photos).
created_at — timestamp, default now.
updated_at — timestamp, auto-update.
Indexes / keys
Index: (user_id)
Notes
Enforce exactly 3 photos per user in the API/service layer.
Only store the object key reliably; object_url is optional.
3) dating_user_cuisines
User’s favorite cuisines (multi-select).
id — string (cuid), primary key.
user_id — string, required.
cuisine — string, required.
Suggested allowed set (validate in app):
NORTH_INDIAN, SOUTH_INDIAN, ITALIAN, JAPANESE, THAI, MEXICAN, MIDDLE_EASTERN, VEGETARIAN_ONLY, VEGAN, JAIN
created_at — timestamp, default now.
updated_at — timestamp, auto-update.
Indexes / keys
Unique: (user_id, cuisine) ← prevents duplicates
Index: (user_id)
4) dating_user_interests
Free-text interests/tags.
id — string (cuid), primary key.
user_id — string, required.
tag — string, required (max 40; lowercase/trim in app).
created_at — timestamp, default now.
updated_at — timestamp, auto-update.
Indexes / keys

Index: (user_id)

6) dating_user_languages
User’s languages (multi-select).
id — string (cuid), primary key.
user_id — string, required.
lang — string, required (e.g., English, Kannada, Hindi; max 40).
created_at — timestamp, default now.
updated_at — timestamp, auto-update.
Indexes / keys

Index: (user_id)
Implementation notes (for your agent)
IDs & timestamps: Use String @id @default(cuid()), createdAt @default(now()), updatedAt @updatedAt in Prisma, mapped to snake_case table names via @@map("…").
No relations needed right now: Keep user_id as a plain string and index it. (This avoids Prisma relation mode issues.)
Validation sets: Enforce all “allowed set” values in the API/service layer (or Zod). Keep DB columns as simple String.
Phone uniqueness: Normalize phone numbers to E.164 format before insert; add the unique index on phone_e164.
Photos: App must enforce exactly 3 photos and sort_order in {0,1,2}.
